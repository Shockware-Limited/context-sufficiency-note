Context retrieval for a language model that edits code is evaluated almost entirely by end-task pass rate. There is no agreed definition of what context is sufficient, and the natural baseline, the principle of total evidence, assumes a reader for whom cost-free information never hurts. Language models are not such readers: their accuracy falls as input grows. This note fixes definitions that take that into account. A change request is a contract $(\Delta, D, I, W)$ with an explicit frame condition and a write-set, checked through an oracle $V_C$ whose unsoundness is named and kept separate. A context K is ε-sufficient for an editor A when A's success on K is within ε of its success on the best context in a stated candidate family, not on the full repository. Within a stylised coverage-times-degradation model we prove, and mechanise in Lean~4, that ε-sufficiency is not closed under superset, with a separation that grows with the amount of irrelevant material, while it is closed under superset for a lossless reader. We state the forward slice as a requirement on the oracle, give three design properties that would make the context a graph query, and report a mutation-based measurement on a real Go repository of how often an interface-preserving change is caught only by tests outside the changed package, together with the token cost of showing those packages to an editor. A planned benchmark, SuffBench, is described. No language-model experiments are reported.
